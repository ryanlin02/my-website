# 支票頁面健檢報告

檢查範圍：`pages/check.html`（460 行，其中 290 行為內嵌 CSS）、`js/check-engine.js`（883 行）
對照基準：已完成優化的 `pages/calculator.html` + `js/calc-ui.js` + `js/calc-storage.js`
檢查日期：2026/07/25

## 摘要

支票頁最嚴重的問題不是「醜」，而是**兩個會讓業務抄錯金額的計算缺陷**，以及**一個讓「保存計算」功能完全形同虛設的按鈕**。

| 級別 | 項目數 | 性質 |
|---|---|---|
| A 級 | 7 | 功能壞掉、金額顯示錯誤 — 建議立即修 |
| B 級 | 5 | 結構性問題 — 是 400 次修改後失控的根源 |
| C 級 | 13 | 體驗與一致性 — 影響操作速度 |

# A 級：會算錯或直接壞掉

## A1. 「歷史記錄」按鈕完全沒有作用 🔴 最嚴重

**位置**：`check-engine.js:748` `toggleHistoryPanel()`

```js
historyPanel.classList.add('active');     // ← 支票頁
```

**原因**
`calculator.css:807` 定義 `.history-panel { display: none; }`，但**全站 CSS 從頭到尾沒有 `.history-panel.active` 這條規則**（已全檔搜尋確認）。加上 `active` 這個 class 不會讓面板顯示出來。計算頁用的是 `panel.style.display = 'block'`（`calc-ui.js:641`），兩邊寫法不同，只有計算頁那套是對的。

**實際後果**
使用者按「保存計算」→ 跳出「支票計算結果已保存！」→ 按「歷史記錄」→ **畫面完全沒反應**。資料真的存進 localStorage 了，但永遠看不到、不能刪、不能編備註。整套歷史功能（含全刪、備註、刪除單筆共 6 個函式、約 120 行程式碼）等於是死的。

**修改方式**
改用 `historyPanel.style.display = 'block' / 'none'`，或在 CSS 補上 `.history-panel.active { display: block; }`。建議前者，與計算頁統一。

**修改後效果**
歷史記錄功能整組復活。業務可以回頭查上一台車怎麼算的、加備註（客戶名／車號）、刪除舊資料。

## A2. 押票金額算出負數時，大寫金額會顯示成「正確的正數」🔴 高風險

**位置**：`check-engine.js:309-317` + `439-457`

```js
depositAmount = totalAmount - (paymentAmount * checkCount) + paymentAmount;
if (depositAmount <= 0) {
    depEl.value = '';                       // 只清了阿拉伯數字欄位
    showToast('錯誤：押票金額必須大於零', true);
    return;                                 // ← depositAmount 仍然是負數，沒有歸零
}
```

接著 `submitCalculatorValue()` 緊跟著呼叫 `updateChineseDisplay()`：

```js
if (depositAmount) {                        // -50000 是 truthy
    el.innerHTML = arabicToChineseNumber(depositAmount, ...) + ' 元整';
}
```

而 `arabicToChineseNumber` 內部是 `Math.floor(Math.abs(number))` — **直接把負號吃掉**。

**實測驗證**
```
arabicToChineseNumber(-50000)  =>  伍萬     ← 應為錯誤／不顯示
```

**實際後果**
輸入 總金額 100 萬 / 繳款 20 萬 / 張數 10 張 → 押票金額 = -70 萬。畫面上「押票金額」欄位是**空白**，但正下方大剌剌寫著 **「柒拾萬元整」**。Toast 兩秒就消失，業務看到一個空欄位配一個看起來很正常的大寫金額，極可能直接抄到支票上。

同時 `.deposit-info-card` 也沒被隱藏，底部卡片會繼續顯示**上一次**的正確金額，形成三個互相矛盾的數字同時在畫面上。

**修改方式**
1. `depositAmount <= 0` 時一併 `depositAmount = 0`、清空 `#deposit-amount-chinese`、隱藏 `.deposit-info-card`
2. `arabicToChineseNumber` 開頭加防呆：`if (!Number.isFinite(number) || number <= 0) return '';`

**修改後效果**
金額不合理時，畫面上不會出現任何大寫金額。杜絕「抄到錯誤大寫」這個唯一會造成實質損失的風險。

## A3. 中文大寫「零」的規則在跨萬位時會漏字 🔴 高風險

**位置**：`check-engine.js:459-507` `arabicToChineseNumber()`

**原因**
函式把數字每 4 位切成一段（chunk）分別轉換，但 `chunkZero` 這個「要補零」的旗標在**每一段開頭都被重設**，段與段之間的零就消失了。

**實測驗證**（節錄）

| 數字 | 目前輸出 | 正確寫法 | 判定 |
|---|---|---|---|
| 1,005,000 | 壹佰萬**伍仟** | 壹佰萬**零**伍仟 | ❌ |
| 10,005,000 | 壹仟萬**伍仟** | 壹仟萬**零**伍仟 | ❌ |
| 1,000,500 | 壹佰萬零伍佰 | 壹佰萬零伍佰 | ✅ |
| 1,200,300 | 壹佰貳拾萬零參佰 | 壹佰貳拾萬零參佰 | ✅ |
| 20,000,001 | 貳仟萬零壹 | 貳仟萬零壹 | ✅ |
| 100,000,005 | 壹億零伍 | 壹億零伍 | ✅ |

失效條件：**高位段的尾數是 0，且低位段的千位不是 0**。1,005,000 這種金額（總價 100 萬出頭的中古車）在重車業務是很常見的數字，不是罕見邊界。

**實際後果**
支票大寫金額漏一個「零」，銀行有權以「文義不清、可被增改」為由退票。這是會造成實質作業損失的錯誤。

**修改方式**
改為在每段結尾記錄「本段最後一位是否為 0」，或改用更穩健的作法：先整串掃描非零數字，遇到連續零只補一個「零」，段落單位（萬／億）另外處理。建議一併寫幾組單元測試固定住。

**修改後效果**
大寫金額在所有 1～9 位數的組合下都正確。這是支票頁的核心產出，值得優先處理。

## A4. 數字鍵盤的小數點鍵按下去會報錯

**位置**：`common-modals.js:115` 對上 `check-engine.js`（缺少定義）

`common-modals.js` 注入的共用鍵盤有一顆 `<button onclick="calculatorDecimal()">.</button>`，但 **`check-engine.js` 從來沒有定義 `calculatorDecimal`**（只有 `calc-ui.js:741` 有）。

**實際後果**
在支票頁按小數點 → console 丟 `ReferenceError: calculatorDecimal is not defined` → 按鈕沒反應、沒震動、沒提示。使用者會以為是螢幕沒感應到而重複按。

**修改方式**
支票頁三個欄位（總金額／繳款／張數）都是整數，不需要小數點。最乾淨的作法是**在支票頁把小數點鍵換成無作用或隱藏**，而不是複製一份 `calculatorDecimal` 過來。可讓 `initCommonModals()` 接受參數決定是否顯示小數點鍵。

**修改後效果**
消除一顆「按了沒反應」的鍵；同時空出的位置可以留給更有用的功能鍵（例如「000」）。

## A5. 金額欄位沒有擋負數

**位置**：`check-engine.js:186-224` `submitCalculatorValue()`

```js
case 'total-amount':
    if (value > 999999999) { ...擋下... }   // 只擋上限
    value = Math.round(value);              // -100 就這樣過關了
```

**原因**
鍵盤沒有 ± 鍵，但**有減號**。使用者輸入 `100 - 200 =` 就會得到 -100，直接被寫進 `totalAmount`。計算頁對應的檢查是 `if (value <= 0)` 一併擋掉（`calc-ui.js:871`），支票頁漏了。

**實際後果**
總金額顯示 `-100`，接著觸發 A2 那條路徑，大寫顯示成 `壹佰元整`。

**修改方式**
三個 case 全部補下限：總金額／繳款 `value <= 0` 擋下，張數 `value < 1` 擋下。

**修改後效果**
不合理的輸入在進入計算前就被攔截，A2 的觸發機率大幅下降。

## A6. 押票金額清空後，下面的大寫金額會殘留

**位置**：`check-engine.js:344-356`（`calculateDepositAmount` 的 else 分支）

else 分支清了 `#deposit-amount`、`#deposit-amount-display`、`#deposit-amount-display-chinese`，**唯獨漏了 `#deposit-amount-chinese`**（欄位正下方那一行）。

**實際後果**
先填完整三個欄位得到正確押票金額 → 把開票張數改成 0 → 押票金額欄位變空白，但正下方的大寫金額**還停在舊的數字上**。畫面上一個空欄位配一個舊金額，跟 A2 是同一種誤導。

**修改方式**
else 分支加上清除 `#deposit-amount-chinese`；更好的作法是統一由 `updateChineseDisplay()` 負責所有大寫欄位的顯示與清除，`calculateDepositAmount()` 只管算數字。

**修改後效果**
畫面上不會再出現「欄位空了但大寫還在」的矛盾狀態。

## A7. 開票張數歸零後，「結束日期」不會清掉

**位置**：`check-engine.js:381-389`

```js
function generateCheckList() {
    if (!checkCount || !startDate) {
        listContent.innerHTML = '';
        card.style.display = 'none';
        return;                    // ← 直接 return，沒呼叫 updateEndDateDisplay()
    }
```

`updateEndDateDisplay()` 只在函式最後一行被呼叫，early return 就跳過了。

**實際後果**
清空張數後，開票列表消失了，但「結束日期」欄位還顯示著舊的日期。業務可能誤以為還有效。

**修改方式**
early return 前先呼叫一次 `updateEndDateDisplay()`（該函式本身已有清空邏輯）。

**修改後效果**
清空張數 = 所有衍生欄位一起歸零，狀態一致。

# B 級：結構性問題（400 次修改後失控的根源）

## B1. `check-engine.js` 與 `calc-ui.js` 有約 200 行完全重複的程式碼

重複清單：`vibrate` / `closeModal` / `calculatorInput` / `calculatorClear` / `calculatorBackspace` / `calculatorOperation` / `calculatorEquals` / `updateCalculatorHistory` / `openCalculator` / `showToast` / `showModal` / `hideModal` / `showConfirmModal` / `hideConfirmModal` — 兩份，逐字幾乎相同。

**原因**
`common-modals.js` 只抽出了共用的 **HTML**，沒有抽出共用的 **JS 邏輯**。

**實際後果**
這正是 A4 的成因：計算頁後來新增了 `calculatorDecimal`，支票頁沒有同步，共用的 HTML 卻已經在呼叫它了。以後每修一個鍵盤 bug，都得記得改兩個檔案 — 400 次修改累積下來，兩邊必然會慢慢分岔。

**修改方式**
新增 `js/common-keypad.js`，把鍵盤與 Toast／Modal 邏輯整組搬過去，`check-engine.js` 只保留 `submitCalculatorValue()` 的欄位驗證（各頁不同的部分）。

**修改後效果**
支票頁 JS 從 883 行降到約 550 行。之後鍵盤只要修一處，四個頁面同時生效，不會再出現 A4 這類「一邊修了一邊沒修」的問題。

## B2. 290 行內嵌 CSS 與 `!important` 混戰

`check.html` 有 460 行，其中 **第 37～327 行全是 `<style>`**，佔了 63%。

**原因與後果**
- `.chinese-row` 同時掛了 `.row` 這個 class，為了推翻 `.row` 的背景、陰影、邊框，一口氣用了 **6 個 `!important`**（`check.html:54-60`）。這代表以後任何全域樣式調整都碰不到這一塊。
- `.check-list-table td:nth-child(1) { width: 60px }` 會同時套用到年份分隔列那個 `colspan="4"` 的 td 上，在 `border-collapse` 下會干擾整張表的欄寬分配。
- 樣式寫在 HTML 裡，每次載入頁面都要重新解析，也無法和 `calculator.css` 一起被瀏覽器快取。

**修改方式**
1. 抽成 `css/check.css`，`check.html` 只留 `<link>`
2. `.chinese-row` 拿掉 `.row` class，改成獨立樣式，6 個 `!important` 全部可以刪掉
3. 表格欄寬選擇器改為 `tr:not(.year-change-row) td:nth-child(1)`

**修改後效果**
`check.html` 從 460 行降到約 170 行，結構一眼看得完。樣式衝突從「靠 `!important` 硬壓」變成「本來就不衝突」，後續改版不會再一改就破版。

## B3. 備註編輯視窗會被手機鍵盤遮住 ⚠️ 違反核心設計原則

**位置**：`check-engine.js:825-850` `openNoteEditor()`

支票頁自己 new 了一個 `className = 'modal-overlay'` 的視窗，而 `.modal-overlay` 是 `align-items: center`（垂直置中）。裡面放的是 `<textarea>` — **這是全站唯一一個會叫出手機鍵盤的元件**。

計算頁對這件事有專門處理：用的是 `.note-editor-modal`（`align-items: flex-start` + `padding-top: 160px`），還有一個 `adjustNoteEditorPosition()` 監聽 `window.visualViewport` 動態調整（`calc-storage.js:296`）。支票頁這套完全沒有。

**實際後果**
在支票頁點「備註」→ 點輸入框 → 鍵盤彈出 → 視窗被推到螢幕外或被鍵盤蓋住，看不到自己在打什麼、也點不到「儲存」。這正好踩到專案設計理念裡明列的「**禁止手機呼叫鍵盤導致畫面排版大幅度移動或者是遮擋**」。

**修改方式**
直接沿用計算頁的 `.note-editor-modal` + `adjustNoteEditorPosition()`，兩頁共用一套備註視窗。

**修改後效果**
鍵盤彈出時視窗固定在上半部，輸入框和儲存鍵全程可見可點。

## B4. 兩套彈窗系統並存

支票頁的日期選擇器用自訂的 `.overlay`（`z-index: 2000`），全站其他彈窗用 `.modal-overlay`（同樣 `z-index: 2000`）。兩套的關閉方式、動畫、按鈕樣式都不同（`.date-picker-button` vs `.modal-btn`）。

**實際後果**
z-index 相同代表未來若有兩個彈窗同時開啟，誰在上面取決於 DOM 順序，不可預期。視覺上也有兩種不同風格的彈窗，違背「習慣之後能快速找到功能」的原則。

**修改方式**
日期選擇器改用 `.modal-overlay` + `.modal-container` + `.modal-btn` 的既有結構，只保留月曆本身的專屬樣式。

**修改後效果**
全站彈窗只有一套，行為（點遮罩關閉、動畫、按鈕位置）完全一致。

# C 級：體驗與一致性

## C1. 頁面頂端多出 65px 的空白

`check.html:38` 強制 `html, body { padding-top: 0 !important; }`，但 `calculator.css:374` 的 `.sticky-header { top: 65px; }` 沒有跟著調整。計算頁有 `.fixed-rate-header` 佔住那 65px，支票頁沒有。

**後果**：往下捲動時，「現在時間」會停在距離頂端 65px 的位置，上方那 65px 是透明的，內容會從它背後穿過去。在手機上白白浪費約 8% 的可視高度，也不好看。

**修改**：支票頁覆寫 `.sticky-header { top: 0; }`。**效果**：多出 65px 可以多顯示約 2 列開票日期。

## C2. 唯讀欄位和可點擊欄位長得一模一樣

`#deposit-amount`（自動算出）和 `#end-date`（自動算出）沒有 `class="readonly"`，看起來跟 `#total-amount`（可點擊叫出鍵盤）完全相同。

**後果**：業務會去點押票金額想改它，點了沒反應。違反「習慣之後能快速找到功能」的設計理念。
**修改**：兩個欄位加上 `class="readonly"`。**效果**：一眼分辨哪些能改、哪些是算出來的。

## C3. 押票金額在畫面上重複顯示三次

目前同時存在：① 押票金額欄位 ② 欄位下方大寫 ③ 底部 `.deposit-info-card`（金額 + 大寫 + 提示）。②③ 的內容完全相同。

**後果**：在「版面盡可能緊湊」的原則下，這張卡片佔掉約 100px 高度，卻只提供「提示文字」這一項新資訊。
**修改**：卡片只保留提示文字，或整張移除、把提示併到欄位下方。**效果**：開票日期列表往上移約 100px，不用捲動就能看到更多張票。

## C4. 開票日期列表沒有金額欄 ⭐ 建議新增

目前列表是「流水號／日期／星期／剩餘張數」。但**實際開票時最容易出錯的，正是「最後一張金額和前面不一樣」**（前 n-1 張 = 繳款金額，第 n 張 = 押票金額）。這個資訊目前要業務自己在腦中對應。

**修改**：加一欄「金額」，最後一張用不同顏色標示為押票。**效果**：業務可以直接照著列表一張一張開，不用心算，這是整頁最能減少實際錯誤的改動。

順帶確認：「剩餘張數」目前是 `checkCount - i`，第 1 張時等於總張數、最後一張是 1（含本張）。若業務習慣是「開完這張還剩幾張」，應改為 `checkCount - i - 1`。這點需要你確認業務慣例。

## C5. 月曆高度會在某些月份跳動

`check-engine.js:562-579` 的補空列邏輯：當 `(firstDayOfWeek + lastDate) % 7 === 0` 時，`remainingCells` 算出 7，導致 `totalDays` 多算一週、`usedRows` 誤判為 6、不再補空列；同時 while 迴圈已經多產生了一個空的 `<tr>`（高度為 0）。

**實測**：2026/1 與 2026/10 只有 5 列，其他月份 6 列。
**後果**：翻月時彈窗高度變化，「確認／取消」按鈕位置跟著跳 — 又一次踩到「禁止畫面大幅度移動」。
**修改**：改成固定產生 6 列（`for (let cell = 0; cell < 42; cell++)`）。**效果**：月曆高度恆定，按鈕永遠在同一個位置，可以盲點。

## C6. 日期選擇器兩個小問題

**(a) 打開時「今天」不會被選取**
`showDatePicker()` 用 `selectedDate = startDate || new Date()`，`new Date()` 帶著時分秒；而月曆格子是 `new Date(y, m, d)`（午夜零點）。`getTime()` 比對永遠不相等，所以今天不會有 selected 樣式。
**修改**：`selectedDate.setHours(0,0,0,0)`。**效果**：打開就看到今天被圈起來，直接按確認即可，少一次點擊。

**(b) 過去日期一律不可選**
`isPastDate` 會把今天以前的日期全部 disabled。但業務常需要回頭試算「客戶去年開始的那批票」。
**修改**：這是業務規則問題，需要你確認。若確定要允許，移除 disabled 即可。

## C7. 歷史記錄的 HTML 和 CSS 對不上

支票頁 `loadCheckHistory()` 用了四個 CSS 裡**根本不存在**的 class：

| 支票頁用的 | CSS 實際有的 | 後果 |
|---|---|---|
| `.no-history` | `.no-data` | 「暫無歷史記錄」變成無樣式裸文字 |
| `.note-btn` | `.detail-btn` | 「備註」鈕沒有樣式 |
| `.history-note-display` | `.history-note-preview` | 備註內容無樣式 |
| `<div><span>總金額：</span>…</div>` | `.history-detail-item` + `.detail-label` / `.detail-value` | 5 個項目塞進 2 欄 grid，第 5 項獨占半格，右半空白 |

也缺少 `.history-list` 外層容器，`gap` 和 `padding` 全部失效。

**修改**：照 `calc-storage.js:140-186` 的結構重寫。**效果**：支票歷史和計算歷史外觀完全一致，不用重新學。

## C8. 歷史記錄不能「載入計算」

計算頁有 `loadLoanToForm()` 可以把歷史回填表單，支票頁只能看不能載。
**修改**：新增 `loadCheckToForm(id)`。**效果**：客戶臨時改條件時，可以載入上次的試算直接改一個欄位，不用四個欄位重打。

## C9. 沒有自動保存／還原

計算頁有 `loanCalculatorAutoSave`，關掉 App 再開資料還在。支票頁完全沒有。
**修改**：`generateCheckList()` 結尾寫入 `checkCalculatorAutoSave`，載入時還原。**效果**：跟計算頁行為一致，不會白打一輪。

## C10. `localStorage` 沒有 try-catch

`saveCheckData()`（`:674`）直接 `localStorage.setItem`，無痕模式或配額滿時會 throw。計算頁的 autoSave 有包 try-catch。
**後果**：儲存失敗時整個按鈕靜默壞掉，還會誤跳「已保存」。
**修改**：包 try-catch，失敗時跳錯誤 Toast。

## C11. 點擊遮罩無法關閉彈窗

計算頁有綁定（`calc-ui.js:973`），支票頁沒有。日期選擇器和歷史面板都只能點特定按鈕關閉。
**修改**：加上遮罩點擊關閉。**效果**：單手操作時可以直接點空白處關閉，少一次精準點按。

## C12. GA 事件完全沒有追蹤

`check.html:26` 定義了 `trackEvent()` 但一次都沒呼叫。計算頁有綁 input focus／change 和 button click。
**後果**：完全不知道支票頁哪些功能被用、哪些沒人用，沒有數據可以決定下一步優化方向。

## C13. 歷史記錄 id 可能碰撞

`id: new Date().getTime()` — 同一毫秒內連按兩次「保存計算」會產生相同 id，刪除一筆時 `filter(item => item.id !== id)` 會**一次刪掉兩筆**。計算頁有同樣問題。
**修改**：改用 `Date.now() + '-' + Math.random().toString(36).slice(2)`。
