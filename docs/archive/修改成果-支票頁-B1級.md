## 一、問題與做法

`common-modals.js` 只抽出了共用的 **HTML**，卻沒有抽出共用的 **JS 邏輯**。結果 `calc-ui.js`（計算頁）和 `check-engine.js`（支票頁）各自維護了一份幾乎逐字相同的鍵盤、Toast、彈窗程式碼。

這正是 A4 那個 bug 的成因：計算頁後來新增了 `calculatorDecimal()`，支票頁沒有同步，但兩頁**共用的鍵盤 HTML 已經在呼叫它了** —— 在支票頁按小數點會直接丟 `ReferenceError`。只要重複的程式碼還在，同樣的分岔遲早會再發生。

新增 `js/common-keypad.js`，把 15 個共用函式與 6 個共用狀態變數集中管理。

### 合併原則

檢查後發現，兩份實作的差異**全部只是防呆寫法，沒有任何一處是邏輯不同**：

```js
// calc-ui.js：直接操作
document.getElementById('calculatorDisplay').textContent = calculatorValue;

// check-engine.js：先確認元素存在
const display = document.getElementById('calculatorDisplay');
if (display) display.textContent = calculatorValue;
```

一律採用「有防呆」的那一版 —— 對兩頁都只會更安全，不會改變行為。

**唯一一處真正的行為差異**：`openCalculator()` 在計算頁會重設 `historyScrollIndicator` 的透明度，支票頁漏了。合併後兩頁都會重設，順手補上支票頁原本缺的行為（上一次的算式捲動提示會殘留）。

### 刻意「不」合併的部分

| 保留在各頁的函式 | 原因 |
|---|---|
| `submitCalculatorValue()` | 各欄位的驗證規則完全不同（計算頁 6 個欄位、支票頁 3 個） |
| `toggleHistoryPanel()` | 載入的資料來源不同（`loadHistoryData` vs `loadCheckHistory`） |
| 備註編輯彈窗 | 兩頁的彈窗結構不同，留待 B3 一併統一 |

硬把這些合併只會製造出一堆 `if (頁面 === 'check')` 的分支，比重複更難維護。

## 三、`let` 重複宣告的陷阱

這次改動有一個必須注意的技術限制：

同一個頁面載入的多個 `<script>`，它們的**頂層 `let` 宣告共用同一個全域語彙環境**。兩個檔案都寫 `let currentInputField` 會直接丟 `SyntaxError: Identifier 'currentInputField' has already been declared`，而且是**整個腳本停止執行**，不是單一函式失效。

所以 `common-keypad.js` 必須排在使用它的檔案之前，兩個 HTML 的載入順序都已調整：

```html
<!-- calculator.html -->
calc-engine.js → common-keypad.js → calc-storage.js → calc-ui.js → common-modals.js

<!-- check.html -->
common-keypad.js → common-modals.js → check-engine.js
```

測試裡加了一道自動檢查，會掃描同一頁載入的所有檔案、比對頂層名稱有無重複 —— 計算頁 69 個、支票頁 56 個名稱，目前皆無衝突。

另外 `sw.js` 的離線快取清單也已加入新檔案，否則離線時兩頁都會開不起來。

## 四、驗證方式

因為這次動到了已經正常運作的計算頁，驗證做得比 A 級更厚。

### 1. 鍵盤行為對照測試 —— 最關鍵的一支

把**改動前**的計算頁鍵盤、**改動前**的支票頁鍵盤、**改動後**的共用模組，分別放進三個獨立沙箱，用 40,000 組隨機操作序列（數字、四則運算、等號、退格、清除、小數點任意組合）同步餵給三者，每按一鍵就比對五個狀態變數是否完全一致。

```
隨機操作序列 40,000 組，累計 299,823 次按鍵
  與「改動前計算頁」狀態不一致: 0
  與「改動前支票頁」狀態不一致: 0
```

這比逐行讀 diff 可靠得多 —— 它直接證明了行為沒變，而不是「看起來沒變」。

### 2. 共用鍵盤測試（52 項）

計算頁與支票頁各跑一遍，並且是**照 HTML 裡真實的 `<script>` 順序**載入：

- 掃描頁面上每一個 `onclick` 屬性，確認指向的函式真的存在（計算頁 26 個、支票頁 15 個，全數通過）—— 這道檢查就是為了防止 A4 那類問題再次發生
- 15 個共用函式在兩頁都可用
- 各頁專屬函式全部健在（計算頁 29 個、支票頁 22 個）
- 鍵盤實際運算：連續輸入、退格、乘除、除以零攔截、連續運算子自動結算
- 小數點：計算頁可用且能輸入 `3.5`；支票頁按鍵已隱藏，但函式存在，不會再有 ReferenceError
- 彈窗：Toast 樣式、確認彈窗 callback、**重複開啟不會累積舊 callback**
- `openCalculator` 帶入欄位現值並去逗號、重設捲動提示

### 3. 計算頁功能測試（49 項）

這是最需要保護的部分，走的是真實操作路徑（開鍵盤 → 輸入 → 確認輸入）：

## 六、這次修改帶來的實際好處

**以後鍵盤只要修一處。** 過去改鍵盤要記得同時改兩個檔案，漏掉就是 A4 那種「一邊修了一邊沒修」的 bug —— 而且完全沒有報錯，只有使用者按下去發現沒反應。

**新的頁面可以直接沿用。** 未來若要幫發票頁或加油頁加上同一套數字鍵盤，只要載入 `common-keypad.js` 再寫自己的 `submitCalculatorValue()` 就好，不用再複製 200 行。

**測試變成安全網。** 這次的重整之所以敢動計算頁，是因為先有了 A 級留下的測試。同樣地，之後 B2、B3 的重整也有了依據 —— 改完跑一次，兩頁的功能有沒有壞立刻知道。

## 七、建議下一步

**B3 備註視窗被手機鍵盤遮住** — 建議接著做，優先度最高

支票頁的備註視窗用的是垂直置中的 `.modal-overlay` 來裝 `<textarea>`，而計算頁有專門處理鍵盤遮擋的 `.note-editor-modal` + `adjustNoteEditorPosition()`（監聽 `visualViewport` 動態調整）。A1 修好之後歷史面板終於打得開，這個問題已經從「碰不到」變成使用者天天會遇到 —— 而且它直接違反專案設計理念裡明列的「禁止手機呼叫鍵盤導致畫面排版大幅度移動或者是遮擋」。

做法是把計算頁那套備註視窗一併搬進共用模組，兩頁共用。**這也正好把 B1 裡刻意保留的最後一塊重複程式碼收乾淨。**

**B2 抽出 `css/check.css`** — 風險最低，可隨時做

`check.html` 目前 480 行裡有 290 行是內嵌 `<style>`。抽出後 HTML 剩約 180 行。同時 `.chinese-row` 拿掉 `.row` class，6 個 `!important` 可以全部刪掉。

**B4 統一彈窗系統、B5 清死碼** — 收尾

B5 現在比原本更單純了：`resultValue`、`updateChineseDisplays()` 已在 A 級與 B1 順手清掉，剩下 `clearField()`（支票頁沒有清除按鈕）與未被呼叫的 `trackEvent()`。
