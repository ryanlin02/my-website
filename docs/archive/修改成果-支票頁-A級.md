## 二、各項修改內容與效果

### A1 — 歷史記錄按鈕完全沒作用

**改了什麼**

```js
// 修改前：全站 CSS 沒有 .history-panel.active 這條規則，加了等於沒加
historyPanel.classList.add('active');

// 修改後：與計算頁一致
historyPanel.style.display = 'block';
```

**效果**
整套歷史功能（查詢、備註、刪除單筆、全刪，約 120 行程式碼）從「完全是死的」變成可用。以前按「保存計算」會跳出「已保存」、資料也真的寫進 localStorage，但按「歷史記錄」畫面毫無反應，存進去的東西永遠看不到。現在可以正常開關、加備註、刪除。

**驗證**：測試確認初始關閉 → 按一下開啟並載入內容 → 再按一下關閉；並確認函式本體已完全不依賴 `active` class。

### A2 — 押票金額為負時，大寫金額顯示成「正確的正數」

這是七項裡風險最高的一項，因為它產出的是一個**看起來完全正常、實際上是錯的大寫金額**。

**改了什麼**

1. 新增 `resetDepositDisplay()`，把押票金額相關的 **6 個顯示位置**一次清乾淨（欄位、欄位下方大寫、卡片金額、卡片大寫、卡片本身、提示文字）。
2. `calculateDepositAmount()` 在金額 ≤ 0 時，**先把 `depositAmount` 歸零**再走清除流程 —— 舊版直接 `return`，把負數留在全域變數裡，後續 `updateChineseDisplay()` 會把它當成有效金額。
3. `arabicToChineseNumber()` 移除 `Math.abs()`，負數／NaN／Infinity 一律回傳空字串。
4. 新增 `renderChineseAmount()`，金額不成立時輸出空字串，不會出現孤零零的「元整」兩個字。

**效果**

| 情境 | 修改前 | 修改後 |
|---|---|---|
| 押票金額算出 -800,000 | 欄位空白，下方顯示 **「捌拾萬 元整」** | 欄位空白，下方也空白 |
| 底部卡片 | 繼續顯示**上一次**的舊金額 | 收起 |
| `depositAmount` 全域變數 | 停留在 -800,000 | 歸零 |

畫面上不再可能出現互相矛盾的三個數字，也徹底杜絕「業務把錯誤大寫抄到支票上」這個唯一會造成實質損失的風險。

**延伸修正**：測試過程發現 `saveCheckData()` 只檢查四個輸入欄位、沒有檢查押票金額本身是否成立，會把一筆押票金額為 0 的紀錄存進歷史。已一併補上檢查。

### A3 — 中文大寫「零」的規則在跨萬位時會漏字

**改了什麼**

演算法由「每 4 位切段、分段轉換」改為「整串由高位往低位掃描」：

- 遇到非零數字：若前面累積過零，先補一個「零」，再寫數字與位單位
- 遇到零：只把「待補零」記起來，連續幾個零也只會補一個
- 走到每個四位段的最低位時，若該段有非零數字才補上 萬／億／兆
- **「待補零」刻意不在 萬／億／兆 之後重設** —— 這正是舊版漏字的根本原因

**效果**

| 金額 | 修改前 | 修改後 |
|---|---|---|
| 1,005,000 | 壹佰萬**伍仟** ❌ | 壹佰萬**零**伍仟 ✅ |
| 10,005,000 | 壹仟萬**伍仟** ❌ | 壹仟萬**零**伍仟 ✅ |
| 705,000 | 柒拾萬**伍仟** ❌ | 柒拾萬**零**伍仟 ✅ |
| 20,005,000 | 貳仟萬**伍仟** ❌ | 貳仟萬**零**伍仟 ✅ |

失效條件是「高位段的尾數是 0，且低位段的千位不是 0」，像 1,005,000 這種總價一百萬出頭的中古車金額在重車業務很常見。大寫漏一個「零」，銀行有權以文義不清、可被增改為由退票。

**驗證**：另外寫了一支「把中文大寫讀回數字」的獨立解析器（邏輯與產生器完全不同），對 **823,017 筆**數字做往返比對，全部一致。包含 1～200,000 全掃、6～8 位數隨機取樣、以及刻意製造大量含零樣式的組合。

### A4 — 數字鍵盤的小數點鍵按下去會報錯

**改了什麼**

`common-modals.js` 注入的共用鍵盤原本寫死一顆呼叫 `calculatorDecimal()` 的小數點鍵，但這個函式只有計算頁（`calc-ui.js`）有定義，支票頁沒有 —— 在支票頁按下去會直接丟 `ReferenceError`。

改為讓各頁自行決定要不要顯示這顆鍵：

```html
<!-- pages/check.html，必須放在 common-modals.js 之前 -->
<script>
    window.KEYPAD_OPTIONS = { decimal: false };
</script>
```

未設定時預設維持顯示，**計算頁行為完全不變**（已迴歸驗證：仍有小數點鍵、0 鍵維持 span 2、鍵數維持 18）。不顯示小數點時，0 鍵自動改為 `span 3` 補滿空出來的格子，鍵盤不會破格。

**效果**
支票頁的三個欄位本來就都是整數，現在鍵盤上不再有一顆「按了沒反應」的鍵。使用者不會再因為以為螢幕沒感應到而重複按。測試也確認了**支票頁鍵盤上 17 顆鍵的 onclick 全部指向已定義的函式**，沒有第二顆地雷。

---

### A5 — 金額欄位沒有擋負數

**改了什麼**

三個欄位補上下限檢查，並把 `Math.round()` 提到驗證之前：

```js
case 'total-amount':
    value = Math.round(value);              // 先四捨五入
    if (value <= 0) { showToast('錯誤：總金額必須大於零', true); return; }
    if (value > 999999999) { ... }
```

舊版先驗證再四捨五入，輸入 `0.4` 會通過檢查、四捨五入後才變成 0，等於繞過了下限。

**效果**
鍵盤雖然沒有 ± 鍵，但有減號 —— 測試已複驗輸入「100 − 200 =」確實會產生 `-100`。修改前這個負數會被直接寫進 `totalAmount` 並觸發 A2；現在在進入計算前就被攔下，`totalAmount` 保持乾淨。開票張數也從「可以是 0」改為「至少 1 張」。

---

### A6 — 押票金額清空後，下面的大寫金額會殘留

**改了什麼**

舊版 `calculateDepositAmount()` 的 else 分支清了三個地方，唯獨漏掉 `#deposit-amount-chinese`（欄位正下方那一行）。現在所有清除路徑統一走 `resetDepositDisplay()`，不再有「這裡清了三個、那裡漏了一個」的問題。`clearAllInputs()` 也改為呼叫同一個函式。

**效果**
把開票張數清掉之後，押票金額欄位和它下方的大寫會**同時**消失。不會再出現「欄位是空的、大寫還停在舊數字上」這種容易誤導的狀態。

---

### A7 — 開票張數歸零後，「結束日期」不會清掉

**改了什麼**

`generateCheckList()` 的 early return 補上 `updateEndDateDisplay()` —— 舊版這個呼叫只寫在函式最後一行，early return 會整個跳過它。

**效果**
測試實測：修改前清空張數後，結束日期會殘留「115年12月10日（四）」；修改後一併清空。業務不會再誤以為那個日期還有效。

## 三、驗證方式

### 1. 整合測試（jsdom，56 項全過）

在模擬瀏覽器環境下實際載入 `check.html` + `common-modals.js` + `check-engine.js`，模擬真實操作流程逐項驗證。除了七個修正點之外，也涵蓋這些迴歸項目：

- 正常路徑：押票金額計算、大寫顯示、底部卡片、提示文字
- 清除全部輸入：六個欄位、兩個大寫、卡片、列表、全域變數
- 開票日期列表：13 張票的日期推算、2 月遇月底自動縮到 28 日、跨年分隔列、結束日期
- 歷史記錄存讀：拒絕不成立金額、正常寫入、面板可開啟看到內容
- **計算頁未受影響**：仍有小數點鍵、0 鍵維持 span 2、鍵數不變

### 2. 大寫金額測試（純 Node，無需安裝套件，44 項全過）

已存進版本庫，之後每次改動 `arabicToChineseNumber` 請先跑一次：

```bash
node tests/大寫金額測試.js
```

涵蓋基本位數、段內補零、跨萬位補零（舊版失效案例）、業務常見金額、防呆輸入，以及 823,017 筆往返比對。

### 3. 語法檢查

`check-engine.js`、`common-modals.js`、`calc-ui.js`、`calc-storage.js` 全部通過 `node --check`。

## 四、建議後續步驟

### 下一批：B 級結構重整

A 級修完、行為確定正確之後，接著處理結構問題才有意義 —— 有了上面兩支測試當安全網，重整過程改壞了會被抓出來。建議順序：

**B2 抽出 `css/check.css`**（先做，風險最低）
`check.html` 目前 470 行裡有 290 行是內嵌 `<style>`。抽出後 HTML 剩約 170 行，一眼看得完。同時 `.chinese-row` 拿掉 `.row` class，6 個 `!important` 可以全部刪掉，樣式衝突從「靠 !important 硬壓」變成「本來就不衝突」。

**B1 抽出 `js/common-keypad.js`**（本批最重要）
`check-engine.js` 與 `calc-ui.js` 有約 200 行逐字重複的鍵盤／Toast／Modal 程式碼。**A4 就是這個結構直接造成的** —— 計算頁後來新增了 `calculatorDecimal`，支票頁沒同步，共用的 HTML 卻已經在呼叫它。這次是用「關掉那顆鍵」處理，但只要重複程式碼還在，下一次分岔遲早會再發生。抽出後支票頁 JS 可從 985 行降到約 600 行。

順帶一提，檢查時發現 `invoice.html` 也載入了 `common-modals.js`，但 `invoice-engine.js` 同樣沒有 `calculatorInput` 等函式。目前那個鍵盤在發票頁是隱藏的死 HTML，不會出錯，但屬於同一個根因，抽共用模組時一併處理掉。

**B3 備註視窗被手機鍵盤遮住** ⚠️ 這一項直接違反專案的核心設計原則
支票頁自己 new 了一個垂直置中的 `.modal-overlay` 來裝 `<textarea>`，而計算頁有專門處理鍵盤遮擋的 `.note-editor-modal` + `adjustNoteEditorPosition()`。A1 修好之後歷史面板終於打得開，這個問題會**立刻變成使用者摸得到的問題** —— 建議緊接著 A 級處理，優先度可以拉到 B 批的最前面。

**B4 統一彈窗系統、B5 清死碼**（收尾）
