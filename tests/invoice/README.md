# 發票頁 - 測試

## 檔案

| 檔案 | 需要 jsdom | 涵蓋內容 |
|---|---|---|
| `verify.js` | 否 | 純函式驗算：格位式大寫、統編檢查碼、稅金計算、反推自洽性、發票期別 |
| `頁面載入測試.js` | 是 | 實際把 `pages/invoice.html` 載起來跑：載入無錯、初始畫面有渲染、17 個互動點不拋錯、二聯式切換、金額連動 |
| `render-samples.js` | 否 | 產生三種情境的擬真發票 SVG，用來目視比對真實發票版面 |

## 執行

```bash
node tests/invoice/verify.js           # 45 項斷言
node tests/invoice/頁面載入測試.js      # 33 項斷言（需 npm install jsdom）
node tests/invoice/render-samples.js   # 產出 inv3.svg / inv3max.svg / inv2.svg
```

`render-samples.js` 產生的 SVG 只是暫時的目視檢查用檔，看完直接刪掉即可，不需要保留在專案裡。

## 已驗證

- 格位式大寫：九格固定、用不到的高位劃掉、「零拾」不可省略
- 統編檢查碼比對 3 組真實統編（取自經濟部商業司開放資料）
- 三聯式（單價未稅、另計 5%）與二聯式（單價含稅、倒推稅額）
- 反推：逐一掃描 1～300000 元，確認「銷售額＋稅額＝總計」恆成立
  （其中 4.8% 的金額需要靠 lockTotal 吸收 1 元進位差）
- 發票本期別（雙月一期）
- 頁面載入、初始渲染、主要互動

## 尚未驗證

- 手機實機的版面、系統鍵盤彈出行為、放大旋轉。jsdom 不排版也不算圖，這幾項只能實機測。

## 三個踩過的坑，改動時請留意

1. **取樣週期陷阱**：正算對不上合約總額的金額有固定週期（每 21 元一次）。
   第一版用 step=7 掃描，週期剛好整除，一個失敗案例都沒抽到、誤判全過。
   驗算稅金時務必逐一掃描，或使用與 21 互質的步長。

2. **大寫寫法有兩種**：一般中文大寫會省略「零拾」，但發票上每個印好的
   單位格都必須填一個數字。抄一般寫法上去，格子數會對不起來。

3. **純函式測試抓不到載入期錯誤**：`DEFAULT_ITEM_NAME` 曾經宣告在 `state`
   之後，const 的暫時性死區讓整頁一載入就 ReferenceError，但當時所有純函式
   測試依然全數通過。動到檔案頂端的宣告順序後，一定要跑 `頁面載入測試.js`。

## 線上統編查詢：已評估並排除

曾評估「輸入統編自動帶出公司抬頭」。經濟部商業司的開放 API
（`data.gcis.nat.gov.tw`）在伺服器端查得到資料，但**從 GitHub Pages 的網頁
發 fetch 會被 CORS 擋掉**（2026/07 於實機 Chrome 驗證，直接貼網址開分頁看得到
JSON，代表網路正常、確實是跨來源限制）。財政部的營業稅籍 CSV 同樣被擋。

靜態網站無法繞過，除非自架後端或把資料預先處理後放進本站（同源）。
目前改採本地客戶名冊：用過的統編與抬頭存在瀏覽器裡，下次輸入統編自動帶出抬頭。
